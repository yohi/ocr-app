# 07. DEC-07 — STOP 発生後の個別再開承認判断資料（R1.1限定是正版）

## 1. Decision Summary

### 1.1 判断する内容
再試験実行中に STOP 条件（ハッシュ不一致、外部通信試行、cgroupリソース制限超過、プロセス未終了、非同期キャンセル等）に抵触して停止した場合に、調査・修復を経て、**承認された特定の単一Stageの再実行を個別に許可するかどうか**の判断枠組みです。

### 1.2 3つの操作権限の明確な分離
STOP 発生時の対応において、以下の3つの操作を混同せず、別個に管理します：
1. **STOP事象の静的調査**: 停止ログの読み取り、cgroup統計の分析、原因仮説の立証。
2. **修復・環境変更**: パラメータ調整、設定変更、フィクスチャ修正（個別の適用承認が必要）。
3. **対象Stageの再実行**: 必須条件の充足が検証された後に行う、単一Stageの再試験実行。

これらを単一の包括承認として事前付与することは厳格に禁止します。

### 1.3 現在のシステム状態と STOP 状態の区別
- **現在の一般的な実行禁止状態**:
  ```text
  NO_EXECUTION_GRANT
  ```
- **実際のSTOP事象発生後**:
  ```text
  STOPPED / NO_AUTOMATIC_RETRY / OWNER_REVIEW_REQUIRED
  ```
現時点では未だテスト実行を行っておらず、実際の STOP 事象は発生していません。したがって、具体的な STOP ID や再開承認が存在するかのように記載してはなりません。

### 1.4 推奨判断
- 現時点では **`HOLD`**（保留）を推奨。
- 理由: STOP は事象が発生して初めて原因・影響・修復内容が確定するものであり、発生前の包括承認は安全境界を破壊するため。

## 2. STOP再開Gateの3段階・非循環契約（FND-ODP-008是正）

R1 における「10条件の1つにOwner承認が含まれ、承認前に承認済みを要求する循環」を解消し、以下の 3 段階の状態遷移を規範的契約として定めます。

```text
[STOP EVENT 発生]
       │
       ▼
[Phase A: Pre-approval Evidence Collection & Verification]
  - 旧条件1〜4, 6〜9 の充足検証（原因特定、ログ保全、修復文書化、HEAD整合性、隔離確認等）
       │
       ▼ (全前提条件 PASS)
[PRE_APPROVAL_GATE_PASS]
       │
       ▼
[Phase B: Human Owner Decision]
  - Human Owner による明示的個別判断（APPROVE / CONDITIONAL_APPROVE / HOLD / REJECT）
  - 旧条件5 の充足（Owner 署名・判断記録発行）
       │
       ▼ (Owner 承認成立)
[Phase C: Post-approval Eligibility Check]
  - 再実行直前の実行資格判定（真正性確認、Stage一致、回数上限、条件充足確認等）
  - 旧条件10（単一Stage限定実行）の適合確認
       │
       ▼ (全適格性確認 PASS)
[AUTHORIZED_SINGLE_STAGE_REEXECUTION] (単一Stageの1回限り再実行)
```

### 2.1 Phase A: 承認前検証条件（Pre-approval Verification）
Human Owner による再実行承認判断の前に、以下の客観的証拠が収集・検証されている必要があります：
1. **STOP原因の客観的特定**: STOP識別子（例: `PID_LIMIT_EXCEEDED`, `HASH_MISMATCH` 等）および発生箇所が文書に記録されていること（旧条件1）。
2. **発生時証跡の完全保全**: 停止直前の標準出力、標準エラー出力、cgroup統計、終了コードが保全されていること（旧条件2）。
3. **修復内容の論理的文書化**: なぜその修復で再発が防止できるのか、原因と対策の因果関係が説明されていること（旧条件3）。
4. **変更範囲の最小限限定**: ソースコード・固定HEADを変更せず、修復が環境設定等の最小限に留まっていること（旧条件4）。
5. **独立安全性確認の完了**: 独立レビュアーによる修復方針のレビュー・合意が得られていること（旧条件6）。
6. **固定HEAD・Manifest再検証**: 作業ツリーが固定HEADと一致し、改変がないことがハッシュで再証明されていること（旧条件7）。
7. **隔離境界の再確認**: 外部ネットワーク遮断、Secrets隔離、ホストDocker Socket非共有が維持されていること（旧条件8）。
8. **cgroup実効性の再確認**: メモリ・PID制限が依然としてアクティブに機能していること（旧条件9）。
9. **再実行対象Stageおよび許容回数の特定**: 再開すべき Stage が1つに特定され、回数上限が設定されていること。

※上記調査・修復操作の実施自体に別の Owner 承認が必要な場合は、その承認を省略してはなりません。

### 2.2 Phase B: Human Owner による明示的判断（Human Owner Decision）
Phase A の全条件充足が客観的証拠により確認された後に、Human Owner が当該 STOP 事案に対して個別の判断を下します（旧条件5）：
- **判断対象**: STOP ID、修復内容、再実行対象Stage、対象VM、実行回数、リソース上限、付帯条件。
- **判断区分**: `APPROVE` / `CONDITIONAL_APPROVE` / `HOLD` / `REJECT`。

### 2.3 Phase C: 再実行直前の実行資格判定（Post-approval Eligibility Check）
再実行プロセスの開始直前に、以下の全項目が確認されなければなりません：
1. 真正な Owner 判断記録（Decision Record ID）が存在すること。
2. 判断記録が当該 STOP ID と一意に結び付いていること。
3. 承認された Stage が単一であり、実行対象と厳密に一致すること（旧条件10）。
4. 実行対象 VM およびリソース枠が承認内容と一致すること。
5. 承認された許容回数（通常1回）を超過していないこと。
6. 条件付き承認の場合、付帯条件がすべて検証・充足されていること。
7. STOP 原因の修復状態が維持されていること。
8. 固定HEAD・隔離境界・cgroup制限が維持されていること。
9. 承認の取消・失効（Revocation）が存在しないこと。

---

## 3. 条件付き承認の厳密な扱い（Fail-closed 契約）

`CONDITIONAL_APPROVE` は、**未充足条件が残る状態での再実行開始を許可するものではありません**。
付帯条件が未充足の間は **`CONDITION_PENDING / EXECUTION_BLOCKED`** として扱われ、すべての条件が検証・充足され、Phase C の適格性判定を通過した後に初めて再実行が可能となります。

---

## 4. STOP識別項目と個別判断の必須フィールド

包括的な一括再開を防ぐため、DEC-07 の判断時には必ず以下の項目を特定して記録します：

- **STOP識別番号**: `STOP-YYYYMMDD-XX`
- **発生Stage**: （Stage 0 〜 Stage 5）
- **検知された事象**: （リソース超過 / 外部通信検知 / ハッシュ不一致 / アサーション失敗 等）
- **修復処置**: （パラメータ調整 / キャッシュ再配置 等）
- **再実行許可Stage**: （承認された1つのStage名）
- **許容試行回数**: （通常1回）

---

## 5. Decision Options（判断選択肢）

- **`APPROVE`**: Phase A 充足確認の上で、対象Stageの1回限りの再実行を承認する。
- **`CONDITIONAL_APPROVE`**: 追加条件を付与して承認する（条件充足まで `EXECUTION_BLOCKED`）。
- **`HOLD`**: 原因分析や修復計画の追加報告を求めて保留する（**初期状態推奨**）。
- **`REJECT`**: 当該再試験の続行を拒否し、試験全体を中止・ロールバックする。
