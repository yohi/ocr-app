# 03. DEC-02 — 独立ローカルGit環境配備判断資料（R1）

## 1. Decision Summary

### 1.1 判断する内容
Stage 3（Group B 認可テスト失敗 3件）を安全に再試験するため、固定HEADに合致し、リモート接続を持たず、ホストの `.git` を共有しない「**独立ローカルGit環境（メタデータ）**」をテストVM内に配備することを承認するかどうかの判断です。

### 1.2 実施する必要性
- Group B の対象テスト（TEST-11, 12, 13）は `.github/workflows/scripts/authorize-routing-start.test.mjs` で実行されます。
- 被テスト実装 `.github/workflows/scripts/authorize-routing-start.mjs` は、内部で `git ls-files` などのGitサブプロセスを呼び出し、ソースファイルの同一性を検証しています。
- 一次テストログには `# fatal: not a git repository (or any of the parent directories): .git` が記録されており、Gitメタデータが存在しないために例外が発生し、fail-closed により認可が拒否されてテストが失敗しています。

### 1.3 推奨判断
- **`APPROVE`** を推奨。
- 理由: テストコードが前提としている実行環境を安全・隔離された形で充足させるものであり、ホストや外部環境への副作用を遮断した設計となっているため。

## 2. Git固定HEAD再現方式とオブジェクト検証契約（FND-ODP-003是正）

単なる `git init` とファイル配置だけでは、固定HEADのコミットオブジェクト（40桁 SHA-1 Git Object ID）を正確に再現・検証できないため、以下の厳密なオブジェクト検証契約を定義します。

### 2.1 Gitオブジェクトとハッシュ概念の厳格な区別
以下の異なるハッシュ概念を混同してはなりません：
- **Git Commit Object ID**: `6b08251170265c444ce8957377e6bfca23b21fd7`（Git固有の 40 桁 SHA-1 オブジェクト識別子）
- **Git Tree Object ID**: 当該コミットに対応するツリーオブジェクトの 40 桁 ID
- **Git Blob Object ID**: 各追跡ファイルに対応する BLOB オブジェクトの 40 桁 ID
- **ファイル内容の SHA-256**: OS ファイルシステム上の個別ファイルバイト列の SHA-256
- **アーカイブの SHA-256**: tar.gz 等の圧縮アーカイブ全体の SHA-256

固定HEADが40桁であることを根拠に「SHA-256」と表現することは禁止します。

### 2.2 オブジェクト来歴検証契約（10要件）
独立ローカルGitメタデータを配備する際は、以下の10要件をすべて満たし検証する必要があります：
1. **固定コミットオブジェクトの取得元**: 正規リポジトリから検証済みエクスポートされたオブジェクトの利用。
2. **treeオブジェクトの検証**: コミットオブジェクトが指す tree オブジェクト ID の整合性確認。
3. **blobオブジェクトの検証**: 各追跡ファイルに対応する blob オブジェクト ID の整合性確認。
4. **追跡ファイルのバイト同一性**: 作業ツリー上のファイルが固定HEADの内容とバイト単位で一致すること。
5. **インデックスと追跡一覧の整合性**: `.git/index` が固定ツリーと一致していること。
6. **`git rev-parse HEAD` の完全一致**: 出力が厳密に `6b08251170265c444ce8957377e6bfca23b21fd7` であること。
7. **`git ls-files` の完全一致**: 出力されるファイル一覧が固定HEADの追跡集合と完全一致すること。
8. **リモート接続の未設定**: `git remote -v` が完全に空であること。
9. **Git hooks の無効化**: `.git/hooks/` 配下のスクリプトがすべて無効化（または空）され、予期せぬ実行経路が存在しないこと。
10. **ホストGitメタデータの完全非共有**: ホスト環境の `.git` ディレクトリを一切マウント・参照・共有しないこと。

**実施方式に関する重要規定**:
固定HEADに対応するオブジェクトの実在性や来歴を検証できない場合は、**`GIT_OBJECT_PROVENANCE_NOT_ESTABLISHED`** と記録し、その状態では DEC-02 を「実行準備完了」と判定してはなりません。また、今回の是正において実際にGitオブジェクトを転送・配備することは禁止されています。

## 3. 原因仮説の客観化と反証可能性

### 3.1 原因ステータスは `CAUSE_UNDETERMINED` を維持
Group B（TEST-11, 12, 13）の失敗原因について、現時点では **`CAUSE_UNDETERMINED`** を公式ステータスとして維持します。
Git環境を配備しただけで Group B が必ず PASS すると保証することは厳禁です。

### 3.2 再試験結果に基づく原因判定基準
1. **`ENVIRONMENT_CAUSE_CONFIRMED`**:
   - 独立ローカルGit配備後、TEST-11, 12, 13 の3件すべてが期待通りの契約で完全 PASS し、環境差分のみが合否を分けたことが立証された場合。
2. **`IMPLEMENTATION_CAUSE_CONFIRMED`**:
   - Git配備後（`git ls-files` が正常終了）、なおテストが失敗し、製品コードの不具合箇所がステップトレースで立証された場合。単なるアサーション失敗の再発だけでは認定不可。
3. **`MIXED_CAUSE`**: 環境要因と実装バグの双方が寄与していた場合。

---

## 4. Decision Options（判断選択肢）

- **`APPROVE`**: 10要件を満たす独立ローカルGit環境の配備を承認する（**推奨**）。
- **`CONDITIONAL_APPROVE`**: オブジェクト来歴検証ログの事前提示を条件として承認する。
- **`HOLD`**: オブジェクト実在性が確認できるまで保留する。
- **`REJECT`**: 配備を拒否する。

## 5. Authorization Scope & Evidence Requirements

### 5.1 承認範囲とセキュリティ境界
- **対象環境**: テスト専用VM内の Stage 3 実行スコープ。
- **Gitメタデータ境界**: リモート未設定・hooks無効化された独立インスタンス。

### 5.2 必要証跡
- **配備後（Stage 3 実行前）**:
  - `git rev-parse HEAD` 出力ログ（`6b082511...`）。
  - `git remote -v` 出力ログ（空）。
  - `git status --porcelain` 出力ログ（クリーン）。
  - hooks ディレクトリの無効化確認ログ。
