# 06. DEC-05 / DEC-06 — Group B / Group C 条件付き診断実験判断資料（R1）

## 1. Decision Summary

### 1.1 判断する内容
Primary 再試験（固定HEADコード完全無変更）を実施した結果、なお原因が特定・解決できない場合に限り、限定的なテストフィクスチャ改善やモック注入を伴う「**診断実験（Diagnostic Experiments）**」の実施を承認するかどうかの判断です。

- **DEC-05**: Group B 診断実験（テストフィクスチャによるGitモック注入）
- **DEC-06**: Group C 診断実験（TEST-14 の非同期クリーンアップ明示フィクスチャ改善）

### 1.2 事前承認表現の厳密な是正（FND-ODP-005是正）
R0 における表現の混乱を是正し、以下の2つの概念を明確に区別します：

- **禁止事項 (`UNCONDITIONAL_ADVANCE_APPROVAL`)**:
  - Primary 再試験の結果が得られる前に、将来の診断実験を無条件・包括的に事前承認すること。
- **必須要件 (`EXPLICIT_PRE_EXECUTION_OWNER_APPROVAL`)**:
  - Primary 再試験の失敗が一次証跡で確認され、具体的な実験範囲、変更パッチ、必要性、危険性が文書化された後、**実験開始前に Human Owner が明示的に個別承認すること**。

### 1.3 推奨判断
- **DEC-05**: 現時点では **`HOLD`**（保留）を推奨。
  - 理由: まず DEC-02（独立ローカルGit配備）に基づく Primary 再試験（Stage 3）の結果を確認すべきであり、無条件事前承認を避けるため。
- **DEC-06**: 現時点では **`HOLD`**（保留）を推奨。
  - 理由: まず Primary 再試験（Stage 4: 単独実行）でのタイムアウト・非同期挙動トレースを確認すべきであり、無条件事前承認を避けるため。

## 2. DEC-05: Group B 診断実験（Gitモック注入）の仕様と制約

### 2.1 実施前提条件
1. Stage 3 において、独立ローカルGit配備下で Primary 再試験が実施され、なお TEST-11, 12, 13 が FAIL すること。
2. 失敗原因が環境起因ではなく、Gitサブプロセス呼び出し周辺の内部動作にあるという仮説と変更パッチが提出されていること。
3. 実験開始前に Human Owner による明示的な個別承認（DEC-05）を取得すること。

### 2.2 許可される操作（Owner承認後）
- テストコード `.github/workflows/scripts/authorize-routing-start.test.mjs` 内の特定テストケースにおいてのみ、Git実行関数（`execFileSync` 等）のモックをフィクスチャとして注入し、返却値をシミュレートして挙動を観測する。
- 診断ログを正規再試験ログとは明確に分離されたディレクトリ（`diagnostic_logs/`）へ記録する。

### 2.3 厳格な禁止事項
- 本番プロダクションコード `.github/workflows/scripts/authorize-routing-start.mjs` の改変。
- 認可判定ロジックの安全側拒否（fail-closed）動作の緩和。
- 診断実験の PASS 結果をもって、正規の Stage 3 PASS と偽装・混同すること。

## 3. DEC-06: Group C 診断実験（TEST-14 フィクスチャ改善）の仕様と制約

### 3.1 実施前提条件
1. Stage 4 において、Primary 再試験が実施され、なお TEST-14 が親ランナーからキャンセルされる、またはハングすること。
2. 観測ログから、未解決Promise、未解除タイマー、または AbortSignal のハンドリング競合が具体的に立証され、フィクスチャ改善パッチが提出されていること。
3. 実験開始前に Human Owner による明示的な個別承認（DEC-06）を取得すること。

### 3.2 セキュリティ期待契約の厳格な維持
TEST-14 のセキュリティ契約は以下の通りであり、いかなる診断実験においてもこれを緩和してはなりません：
- **期待結果**:
  - `grant.allowed === false`
  - `grant.reason === 'egress_denied'`
- **禁止事項**:
  - 外側への例外送出（throw/reject）を合格と判定すること。
  - プロセスのハングや外側タイムアウト（60秒）による強制終了を合格と判定すること。
  - 機密情報（トークン等）をログや `reason` に露出させること。

### 3.3 許可される操作（Owner承認後）
- `.github/workflows/scripts/authorize-decision-egress.test.mjs` において、モック fetch の AbortSignal 解除やタイマーのクリーンアップを明示的に行うフィクスチャ修正を適用し、親ランナーのキャンセルが解消されるか検証する。
- 診断ログを `diagnostic_logs/` 配下に完全分離して記録する。

## 4. Decision Options（判断選択肢）

### DEC-05 (Group B 診断実験)
- **`APPROVE`**: 実験条件・パッチ提示確認の上、実験開始前の個別承認として承認する。
- **`CONDITIONAL_APPROVE`**: 追加のログ保全条件を付与して承認する。
- **`HOLD`**: Stage 3 Primary 再試験の結果が出るまで保留する（**推奨**）。
- **`REJECT`**: モック実験を認めず、コード変更なしの調査のみとする。

### DEC-06 (Group C 診断実験)
- **`APPROVE`**: 実験条件・パッチ提示確認の上、実験開始前の個別承認として承認する。
- **`CONDITIONAL_APPROVE`**: 追加のトレース取得条件を付与して承認する。

- **`REJECT`**: フィクスチャ改変を認めない。
